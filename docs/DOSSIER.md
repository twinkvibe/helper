# Досье

Личные записи о людях и событиях: чтобы перечитать и вспомнить, что происходило,
кто в чём участвовал и что именно было сказано. Раздел доступен по адресу
`/dossier` и синхронизируется между устройствами через Supabase.

## Что уже реализовано

- **Люди**: имя, «также известен как» (псевдонимы), кем является, теги, Markdown-заметки.
- **Записи (события)**: заголовок, Markdown-текст, дата события, теги, участники, фотографии.
- **Связи**: у одной записи может быть несколько людей; у человека — много записей.
- **Поиск и теги** по людям и записям; сводка «Все записи» как общая лента.
- **Фотографии**: приватное хранилище `dossier-media`, доступ по короткоживущей подписанной ссылке.
- **ИИ-помощник** (необязательно): кнопка «Уточнить с ИИ» в диалоге записи.

## Модель данных

| Таблица | Назначение |
| --- | --- |
| `dossier_people` | человек = его досье: `name`, `aliases[]`, `relation` (кто это), `relationship` (статус отношений глазами владельца), `facts` (jsonb-массив `{key, value}`: адрес, телефон, день рождения…), `avatar_path` (приватный объект в `dossier-media`), `bio`, `tags[]`. |
| `dossier_entries` | событие: `title`, `body` (Markdown), `occurred_at` (день и час), `mood`, `tags[]`, `attachments` (jsonb). |
| `dossier_entry_people` | связь событие↔человек (многие-ко-многим), `user_id` для RLS. |
| `dossier_person_links` | ссылки человека на других людей: `person_id`, `linked_person_id`, `label` (кем приходится). |

Все таблицы принадлежат владельцу. RLS повторяет правила `todos`: доступ есть
только у владельца и только пока профиль активен и пароль не требует смены.
Анонимного доступа нет вовсе: ни одна политика не выдаёт права `anon`, бакет
`dossier-media` приватный (`public = false`).

`attachments` — массив объектов `{ path, name, type, size }`; `path` указывает на
объект в приватном бакете `dossier-media` с префиксом `<userId>/<entryId>/`
(у аватарок — `<userId>/avatars/`).
Интерфейс получает подписанные ссылки через `storage.createSignedUrls` и не хранит
постоянных публичных URL. Фото и скриншоты показываются миниатюрами, видео
(`video/mp4`, `video/webm`, до 25 МБ) — встроенным плеером. В CSP для этого есть
`media-src https: blob:`.

Лента записей группируется по календарным дням (по дате события, иначе по дате
создания): день-заголовок, внутри записи по времени.

## ИИ-помощник

Секреты живут только на сервере. Frontend вызывает Edge Function `account`:

- `dossier:analyze` — разбор одной записи: факты, сомнения, уточняющие вопросы;
- `dossier:review` — разбор карточки человека: проверяет статус отношений и факты
  по всем его записям, предлагает конкретные правки и список вопросов.

Переменные функции: `AI_CHAIN` (цепочка провайдеров, см. `docs/TELEGRAM.md`;
старые `AI_API_KEY` / `AI_BASE_URL` / `AI_MODEL` — запасной одиночный вариант).

Возможные следующие шаги (пространство для развития):

1. **Разбор свободного текста в структуру**: модель возвращает JSON
   `{ title, occurred_at, tags, people, facts, doubts, questions }`, интерфейс
   подставляет это в форму. Требует строгого JSON-режима и валидации ответа.
2. **Сводка по человеку**: собрать все записи человека и попросить краткую
   хронологию и открытые вопросы.
3. **Вопрос-ответ по досье**: выбрать релевантные записи по тегам/поиску,
   передать их как контекст и ответить на вопрос «было ли это на самом деле?».
4. **Журнал ИИ-запросов**: писать в `audit_logs` факт вызова, длину текста и
   модель (сообщать пользователю, что текст уходит внешнему провайдеру).

Приватность: содержимое записи покидает ваш Supabase и уходит провайдеру LLM.
Для чувствительных досье это осознанный компромисс; ключ и провайдер выбирает
владелец. Никогда не помещайте `AI_API_KEY` во frontend или `VITE_`-переменные.

## Доступ с телефона

- Приложение адаптивно и добавляется на домашний экран как PWA
  (`public/manifest.webmanifest`, `display: standalone`).
- Данные те же, что на компьютере: вход под своим аккаунтом, RLS-защита сохраняется.

### Telegram-бот (проект)

Идея: отправлять в бота быстрые записи «голосом с улицы» и получать напоминания.
Практичная схема:

1. Edge Function `telegram` принимает webhook от Telegram (`POST`), проверяет
   `X-Telegram-Bot-Api-Secret-Token`, читает `BOT_TOKEN` из секретов функции.
2. Привязка аккаунта: пользователь получает одноразовый код в интерфейсе, отправляет
   боту `/start <код>`; функция пишет `chat_id` в отдельную таблицу `telegram_links`
   (owner-only RLS).
3. Бот создаёт записи от имени владельца через `service_role` **после** проверки
   связи `chat_id ↔ user_id`.
4. Секреты: `BOT_TOKEN`, `WEBHOOK_SECRET` — только в секретах функции, никогда в коде.

Риски: бот обходит вход по паролю, поэтому привязка одноразовая и с ограничением
по времени, а `chat_id` — строго персональный ключ доступа.

## Порядок развёртывания

1. Применить `supabase/migrations/20260924_dossier.sql` и затем
   `supabase/migrations/20260925_dossier_profile.sql` (для установок до них — по
   порядку после предыдущих миграций). Для нового проекта достаточно `schema.sql`.
2. Redeploy Edge Function `account`, если менялась её логика, и задеплой
   `telegram` при первом появлении:
   `supabase functions deploy account telegram --project-ref <ref>`.
3. Задать секрет `AI_CHAIN` (и `BOT_TOKEN` + `WEBHOOK_SECRET` для бота).
4. `npm test && npm run build`.

GitHub Pages публикует только frontend. Миграции и Edge Functions деплоятся
отдельно и никогда не применяются workflow автоматически.
