# helper

Личное пространство на GitHub Pages: вход по логину и паролю, задачи в Supabase, локальный Markdown и админка. Frontend: Vite + JavaScript; backend: Supabase Auth, PostgreSQL с RLS и Edge Function `account`.

## Подключение Supabase — один раз

Публичный ключ уже записан в локальный `.env.local` (не попадает в Git). Он не даёт права создавать таблицы или администрировать Auth. Нужны следующие действия владельца проекта:

1. В Supabase → SQL Editor выполни содержимое `supabase/schema.sql` **один раз**. Если ранее запускалась другая схема, сначала нужна миграция: этот файл рассчитан на новый проект.
2. Authentication → Sign In / Providers: выключи **Allow new users to sign up** и anonymous sign-ins. Оставь вход по email/password. Наш интерфейс преобразует логин в служебный email `<логин>@users.helper.invalid`; почта не используется для восстановления. Восстановление — через администратора.
3. Authentication → Users → Add user → Create new user: email `dustin@users.helper.invalid`, временный пароль, который ты выбрал, **Auto Confirm User** включён. Запрошенный `123123` можно использовать только если настройки политики Supabase его разрешают. Не снижай политику проекта ради этого пароля: если он отклонён, задай более длинный временный пароль. Не сохраняй пароль в репозитории.
4. В SQL Editor создай профиль первого администратора:

   ```sql
   insert into public.profiles (id, username, role, must_change_password)
   select id, 'dustin', 'admin', true
   from auth.users where email = 'dustin@users.helper.invalid';
   ```

   Убедись, что вставлена ровно одна строка. До смены пароля RLS запрещает доступ к задачам, серверная функция запрещает администрирование.
5. Edge Functions → создай функцию **account**, вставь `supabase/functions/account/index.ts` и опубликуй. Выключи платформенную опцию **Verify JWT / Enforce JWT verification** для этой функции: в коде каждый запрос проверяется через `auth.getUser(token)`, затем права читаются из базы. Это нужно для совместимости с текущими ключами. Стандартные `SUPABASE_URL`, `SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY` предоставляются окружением функции; никогда не добавляй service role в frontend.
6. Войди как `dustin` и замени временный пароль на новый (12–128 символов). Затем в админке создавай пользователей, блокируй/разблокируй их и сбрасывай пароли. Интерфейс не позволяет создавать других администраторов или блокировать администратора.

Альтернатива публикации функции через панель, если установлен Supabase CLI:

```sh
supabase login
supabase link --project-ref aoukafxzpndqwrjwgdoz
supabase functions deploy account
```

## Локальный запуск

Node.js 22.12+:

```sh
npm ci
cp .env.example .env.local
# Заполни .env.local публичными URL и publishable key своего проекта.
npm run dev
```

Открыть `http://127.0.0.1:5173/helper/`. Если `.env.local` уже настроен, не перезаписывай его. Строгая CSP рассчитана на production; для проверки без ограничений HMR удобнее `npm run build && npm run preview` (без live reload). Для локальной проверки функции разрешены origin `http://127.0.0.1:5173` и `http://127.0.0.1:4173`.

## GitHub Pages

В репозитории Settings → Secrets and variables → Actions → **Variables** добавь:

- `VITE_SUPABASE_URL` — Project URL;
- `VITE_SUPABASE_PUBLISHABLE_KEY` — публичный publishable key.

Settings → Pages → Source: **GitHub Actions**. После push в `main` workflow проверит приложение, соберёт и опубликует его по адресу `https://twinkvibe.github.io/helper/`. Серверную функцию нужно публиковать отдельно при её изменениях. GitHub Actions не получает административный ключ Supabase.

## Проверка

```sh
npm test
npm run build
```

После настройки удалённого проекта:

- анонимный запрос к `todos` не получает данные;
- вход под новым аккаунтом ведёт на обязательную смену пароля;
- пользователь A не читает и не изменяет задачи пользователя B даже прямым запросом к REST API;
- обычный пользователь получает 403 на `account` с `action: list/create/block/reset`;
- заблокированный пользователь со старым JWT не получает задачи и 403 на серверные операции;
- вход с «запомнить меня» переживает перезапуск браузера; без него токен хранится в sessionStorage вкладки;
- Markdown сохраняется после обновления страницы и выхода; для другого аккаунта используется отдельный ключ;
- вредоносный HTML в Markdown не запускается, внешние картинки не загружаются.

## Границы защиты и хранения

Пароли обрабатывает Supabase Auth; в репозитории и таблицах приложения их нет. Привилегии находятся в `profiles`, клиент имеет только SELECT своего профиля. Нельзя повысить роль изменением user_metadata. Изменения задач идут через Supabase SDK; значения не становятся SQL-кодом. Текст задач выводится через textContent, Markdown очищается DOMPurify. CSP запрещает сторонние скрипты, фреймы внутри страницы, формы и внешние изображения. Pages не позволяет задавать все HTTP security headers, в частности `frame-ancestors` через meta не работает.

Pages и код интерфейса публичны. Серверная защита распространяется на данные и операции; клиентский Markdown-редактор сам по себе нельзя сделать недоступным для человека, скачавшего код. Блокировка прекращает серверный доступ, но не стирает ранее скачанные данные с чужого устройства.

Markdown хранится в localStorage отдельно для каждого UUID пользователя. Приложение не удаляет его при выходе, но это не резервная копия и не шифрование: очистка данных сайта, приватный режим, политика браузера или сбой диска могут удалить заметку. Все приложения на `twinkvibe.github.io` имеют общий origin и потенциально могут обращаться к этому хранилищу. Для недоверенных соседних сайтов нужен отдельный домен. Уже открытый браузерный профиль тоже имеет доступ к локальным данным. Cookies для текста не используются из-за ограничений размера.

Смена пароля требует текущий пароль. Сброс администратором сначала закрывает доступ к задачам до смены пароля; блокировка проверяется по актуальной записи базы, а не только по JWT. В Supabase настрой ограничения частоты входа/политику паролей по требованиям проекта. Абсолютной защиты от всех атак этот стартовый проект не обещает.
